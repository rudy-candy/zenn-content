## 1-1 脆弱性診断とは何か

脆弱性診断とは、一言で言えば**「Webアプリの健康診断」**だ。

病院の健康診断では、医師が血液検査や画像診断を通じて体の異常を早期に見つける。脆弱性診断もこれと同じで、セキュリティの専門家がWebアプリケーションを隅々まで調べ、攻撃者に悪用される前に弱点を見つけ出す。

違いがあるとすれば、診断する対象が「人の体」から「Webアプリ」に変わっただけだ。

では誰が「患者」になるのか。オンラインバンキング、ECサイト、業務システム——世の中にあるすべてのWebサービスが対象になりえる。個人情報や決済情報を扱うサービスほど、診断の必要性が高い。

## 1-2 診断の現場はどんな雰囲気か

脆弱性診断の仕事は、華やかさよりも地道さが求められる。ハリウッド映画のように派手なハッキングシーンはなく、実際はブラウザとツールを使いながら、ひとつひとつのリクエストを丁寧に確認していく作業だ。

年間で約30〜40件の診断を担当している中で、今でも印象に残っているケースがある。

ある企業の社内向けWebアプリを診断していたときのことだ。そのアプリは営業部・管理部など複数の部門が利用しており、それぞれ閲覧できる情報が分かれているはずだった。ログイン後に自分の部門の画面を操作していると、あるパラメータを変えるだけで別の部門の情報がそのまま表示された。営業部のアカウントで管理部の情報が見える。逆もしかりだ。

システムは「ログインしているか」は確認していたが、「その情報を見る権限があるか」は確認していなかった。

企業にとって部門間の情報管理は重要なはずだ。にもかかわらず、その境界線はたった一箇所の実装漏れで崩れていた。診断して初めてわかる、こういった「見えない穴」を探すのがこの仕事だ。

## 1-3 1件の診断はどう進むか

1件の診断は、おおよそ次の流れで進む。

**STEP 1：事前準備（キックオフ）**
クライアントから診断対象のURLリスト・仕様書・テスト用アカウントを受け取る。「どこまで診ていいか」というスコープをこの段階で合意しておくことが重要だ。ヒアリングで確認する具体的な項目については**第3章**で詳しく説明する。

**STEP 2：環境確認・疎通確認**
診断環境（本番またはステージング）に接続できるかを確認し、テストアカウントでログインできるかを確かめる。Burp Suiteのプロキシ設定もここで整える。Burp Suiteの環境構築手順については**第2章**を参照してほしい。

ここで注意が必要なのは、**本番環境かステージング環境かによって診断の進め方が変わる**点だ。本番環境では実際のデータや利用者に影響が出る可能性があるため、診断できる項目やパラメータに制限がかかることがある。ステージング環境であれば比較的自由に試せるが、本番と挙動が異なる場合もある。事前にどちらで診断するかを確認しておくことが欠かせない。

**STEP 3：クローリング**
対象アプリを実際に操作しながら、すべての画面・リクエストをBurp Suiteに記録していく。Burp SuiteのProxy機能を使った具体的な操作方法は**第9章**で説明する。

ここで初心者が驚くことがある。**クローリングをしていると、事前に渡されたURLリストにない画面やAPIが見つかることがある**。隠し機能というわけではなく、クライアント側が把握しきれていなかった画面や、動的に生成されるエンドポイントだ。こうした「想定外の診断対象」が増えることは実務でよくある。

**STEP 4：診断実施**
記録したリクエストに対して、ひとつひとつ脆弱性を確認していく。ツールによる自動スキャンと手動操作を組み合わせるが、**手動操作の比重が非常に高い**。各脆弱性の具体的な検査手順は**第5〜8章**で解説する。

特に、文字列を入力して画面遷移が発生するような操作の中で脆弱性が現れることが多いためだ。自動ツールは静的なリクエストには強いが、「入力→遷移→結果」という一連の流れの中に潜む脆弱性は、人間が実際に操作しながら確認するしかない。

また、診断を進める中でWebサイトの構造が複雑であることが判明し、**追加のテスト用アカウントが必要になる場合もある**。権限の異なるアカウントがなければ確認できない脆弱性があるためだ。このような場合はクライアントに連絡して追加アカウントを受け取り、診断を続ける。

**STEP 5：報告書作成**
見つかった脆弱性を整理し、リスクレベル・再現手順・推奨対策を記載した報告書を作成して納品する。報告書の書き方・構成・各社の違いについては**第10章**で詳しく説明する。

**STEP 6：再診断**
クライアントが脆弱性を修正した後、正しく直っているかを確認する。再診断での確認ポイントや注意点は**第10章**および**第11章**でも触れている。

## 1-4 どんな脆弱性が実際に見つかるか

実務で最もよく見かけた脆弱性のひとつが、先ほど紹介した**認可不備（アクセス制御の欠陥）**だ。

「ログインさえできれば何でも見られる」という実装になっているケースは思いのほか多い。本来は「このユーザーはこの情報だけ見られる」という制御が必要なのに、その部分が抜け落ちている。

もうひとつ、実務で頻繁に見かけたのが**HTTPセキュリティヘッダーの不足**だ。

HTTPヘッダーとは、ブラウザとサーバーがやり取りする際に添付される「付加情報」のようなものだ。この中にはセキュリティ上の指示を伝えるものがあり、適切に設定されていないと攻撃者に悪用される余地が生まれる。

設定し忘れても画面上は何も変わらないため、開発中に見落とされやすい。しかし診断ツールでレスポンスを確認すると一目でわかる。実務でよく不足していたヘッダーを以下にまとめる。

| ヘッダー名 | 役割 |
|---|---|
| **HTTP Strict Transport Security（HSTS）** | 必ずHTTPSで通信するよう強制する。HTTPでアクセスしてきたブラウザを自動的にHTTPSへ誘導する |
| **HTTP Public Key Pinning（HPKP）** | サーバーの証明書を固定し、偽の証明書による中間者攻撃を防ぐ（現在は主要ブラウザでサポート終了・非推奨） |
| **X-Frame-Options** | 自サイトが別サイトのiframeに埋め込まれるのを防ぐ。クリックジャッキング攻撃への対策 |
| **X-XSS-Protection** | ブラウザ組み込みのXSSフィルターを有効にする（現在は主要ブラウザでサポート終了・非推奨） |
| **X-Content-Type-Options** | ブラウザがファイルの種類を勝手に推測する「MIMEスニッフィング」を防ぐ |
| **Content-Security-Policy（CSP）** | 読み込んでいいリソースの場所をホワイトリストで制限する。XSS対策として特に重要 |
| **X-Permitted-Cross-Domain-Policies** | Adobe FlashやAcrobatなどが別ドメインのデータを読み込むのを制限する |
| **Referrer-Policy** | ページ遷移時にどこからアクセスしてきたかという情報（Refererヘッダー）をどこまで送るかを制御する |
| **Expect-CT** | 証明書の透明性（Certificate Transparency）ログへの記録を要求し、不正な証明書の発行を検知しやすくする（2022年以降は非推奨・事実上不要） |
| **Feature-Policy（Permissions-Policy）** | カメラ・マイク・位置情報など、ブラウザの機能へのアクセスを制限する |

これだけ種類があると「全部設定するのは大変では」と思うかもしれない。しかし裏を返せば、**これらが設定されていないサイトは今も多く存在する**ということだ。診断の現場では、この一覧をチェックリストとして使うだけで複数の指摘が見つかることが珍しくない。

## 1-5 この本で学べること・学べないこと

### この本で学べること

本書は「Webアプリ脆弱性診断の実務を知りたい人」に向けて書いた。年間約30〜40件の実診断から得た経験をもとにしているため、教科書的な説明よりも「現場でどうやっているか」に重点を置いている。

読み終えたあとには、次のことができるようになる。

- 脆弱性診断の一連の流れ（ヒアリング→クローリング→診断→報告書→再診断）を説明できる
- Burp Suiteを使った基本的な診断操作ができる
- SQLインジェクション・XSS・CSRF・認可不備などの主要な脆弱性の検出方法がわかる
- 実務レベルの報告書の構成と書き方がわかる
- CTFやバグバウンティに挑戦する際の土台になる知識が身につく

### この本で学べないこと

正直に書いておく。本書を読んでも、すぐに「プロの診断員」になれるわけではない。

**ネットワーク・インフラ系の診断**はカバーしていない。本書はWebアプリに特化しており、サーバーやネットワーク機器の診断手法は扱わない。

**最新の攻撃手法への対応**も本書の範囲外だ。セキュリティの世界は日々変化しており、本書で紹介した知識が陳腐化する可能性がある。診断員として働くには継続的な情報収集が欠かせない。

**ソースコードレビュー**も含まない。本書はブラックボックス診断（ソースコードなしで外部からテストする方法）を前提にしている。

### 次のステップ

本書を読み終えたあとは、次の方向に進むことをおすすめする。

- **実際に手を動かす**：HackTheBoxやCyLab Security Academy（旧picoCTF）で実践する
- **バグバウンティに挑戦する**：サイボウズなど日本語で参加できるプログラムから始める
- **OWASP Testing Guideを読む**：本書の各章の元になっている詳細なガイドライン
- **資格取得を目指す**：CEH・OSCP・情報処理安全確保支援士など

脆弱性診断は「知識」と「経験」の両方が必要な仕事だ。本書が現場に踏み出すための最初の一歩になれば幸いだ。
