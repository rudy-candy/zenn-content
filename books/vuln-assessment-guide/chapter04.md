## 4-1 OWASP Top 10とは

OWASP（Open Web Application Security Project）は、Webアプリのセキュリティ向上を目的とした非営利団体だ。その中で最も有名なドキュメントが「OWASP Top 10」で、Webアプリケーションで特に深刻なリスク上位10項目をまとめたものだ。数年ごとに改訂されており、現在は**2021年版**が最新だ。

診断の現場ではこのTop 10がチェックリストの土台として使われることが多い。セキュリティを学ぶ上での共通言語でもあるため、まずここを押さえておくと後の章の内容が格段に理解しやすくなる。

## 4-2 OWASP Top 10 2021 一覧

| # | リスク名 | 概要 |
|---|---|---|
| A01 | アクセス制御の不備 | 権限のないユーザーが他人のデータにアクセスできてしまう |
| A02 | 暗号化の失敗 | 重要情報が暗号化されずに通信・保存されている |
| A03 | インジェクション | SQLi・XSS・OSコマンドなど不正な入力による攻撃 |
| A04 | 安全が確認されない不安全な設計 | 設計段階でのセキュリティ考慮の欠如 |
| A05 | セキュリティの設定ミス | 不要な機能の有効化・デフォルト設定のまま使用など |
| A06 | 脆弱で古くなったコンポーネント | 既知の脆弱性があるライブラリの使用 |
| A07 | 識別と認証の失敗 | セッション管理の欠陥・弱いパスワードの許容など |
| A08 | ソフトウェアとデータの整合性の失敗 | 検証されていないコードやデータの使用 |
| A09 | セキュリティログとモニタリングの失敗 | 攻撃の検知・記録ができていない |
| A10 | サーバーサイドリクエストフォージェリ | サーバーを踏み台にした内部リソースへのアクセス |

## 4-3 実務でよく見つかるものとそうでないもの

教科書でTop 10を見ると10項目が並列に見えるが、実務では出現頻度に大きな差がある。複数年度にわたる担当案件の検出データをもとに整理すると、以下のことがわかった。

### よく見つかる（ほぼ毎回出る）

**A03 インジェクション（XSS・SQLi）**
XSSとSQLインジェクションはほぼすべての案件で確認項目に上がる。診断対象に何らかの入力フォームがあればまず確認する項目だ。

**A05 セキュリティの設定ミス（ヘッダ不備・エラー処理）**
セキュリティヘッダの未設定やキャッシュ制御の問題はほぼ毎回検出される。設定し忘れるだけで指摘になるため件数が多い。エラーメッセージに内部情報が含まれているケースやシステム情報が露出しているケースも同様だ。

**A07 識別と認証の失敗（アカウントロック・ログアウト）**
ログイン試行回数の制限なし・ログアウト後のセッション残存は、実装を確認するだけで判定できるため検出頻度が高い。

**A01 アクセス制御の不備（強制ブラウジング）**
URLを直接入力して本来アクセスできないページに到達できる「強制ブラウジング」は、ほぼ毎回確認項目に上がる。

### 出ることもあるが件数は少ない

**A02 暗号化の失敗**
HTTPS化が当たり前になった現在、通信経路の暗号化漏れは以前より減っている。ただし古いシステムやHTTP混在ページでは今も見つかる。

**A06 脆弱で古くなったコンポーネント**
jQueryなど古いバージョンのライブラリが使われている場合に検出される。脆弱性情報の収集が追いついていない現場では多く見つかる。

### 実務では検出しにくいもの

**A04 安全が確認されない不安全な設計**
設計レベルの問題であるため、通常のWebアプリ診断（ブラックボックス診断）では発見しにくい。ソースコードレビューや設計書の確認が必要になる。

**A09 ログとモニタリングの失敗**
診断員の立場からは「ログが取れているか」を直接確認できないケースがほとんどだ。

## 4-4 Top 10は「出発点」として使う

OWASP Top 10はセキュリティの全体像を把握するのに優れたドキュメントだが、実務で使う際は注意点がある。

**Top 10に載っていない脆弱性もある。** ディレクトリ・リスティングやオープンリダイレクトなど、実務でよく検出される項目がTop 10の枠に収まらないこともある。

**重要度はシステムによって変わる。** 決済機能のあるECサイトと社内向けの情報管理ツールでは、同じXSSでも深刻度が異なる。Top 10の順位はあくまで一般的な指標であり、対象システムに応じた判断が必要だ。

Top 10を「すべき確認項目の地図」として使いながら、実際の診断対象に合わせて優先度を調整していくのが実務の進め方だ。

## 4-5 各項目の基本的な確認方法

Top 10の各項目を実際にどう確認するか、実務での基本的な手順を簡単にまとめる。

**A01 アクセス制御の不備**
ログイン後に表示されるURLを、ログアウト状態や別アカウントでそのまま開く。表示されれば不備あり。IDをインクリメントしてURLを叩く（例：`/user/100` → `/user/101`）のも有効だ。

**A03 インジェクション**
入力フォームやURLパラメータに `'` や `<script>` などの特殊文字を入力し、エラーや意図しない動作が起きないかを確認する。Burp SuiteのRepeaterで繰り返し試しやすい。

**A05 セキュリティの設定ミス**
Burp Suiteのレスポンスヘッダを確認し、セキュリティヘッダの有無をチェックする。第2章で紹介したヘッダ一覧を使えばそのまま確認できる。

**A07 識別と認証の失敗**
ログアウト後に戻るボタンでページが表示されないか確認する。パスワード変更画面で現在のパスワードを要求するかも確認ポイントだ。

**A06 脆弱で古くなったコンポーネント**
ページのソースを表示してjQueryなどのバージョンを確認する。バージョンがわかれば既知の脆弱性データベース（NVDなど）で検索する。
