## 10-1 報告書の役割

脆弱性診断の報告書は、クライアントへの最終納品物だ。どれだけ優れた診断ができても、報告書がわかりにくければ対策につながらない。技術者でない担当者が読むこともあるため、「何が問題で・どう危険で・何をすればよいか」が伝わる構成にする必要がある。

---

## 10-2 報告書の全体構成

実務の報告書は大きく4つのパートで構成される。

```
1. エグゼクティブサマリー  ← 経営層・非技術者向けの概要
2. 対策指針              ← 早急の対策と恒久的な対策
3. 診断結果              ← 指摘一覧と危険度基準
4. 詳細                  ← 各脆弱性の技術的説明
```

### エグゼクティブサマリー

報告書の冒頭に置く1〜2ページのサマリーだ。経営層が読む想定で、専門用語を避けて書く。

サマリーは「発見した脆弱性の件数」「その中で最も深刻なものがどんな被害につながるか」「軽微な指摘の概況」の3点を中心に書く。技術名（XSSなど）を出す場合も、それによって何が起きるかをセットで説明する。「クロスサイト・スクリプティングがありました」で終わらせず、「第三者が利用者のブラウザ上で任意のスクリプトを実行できる状態にあります」のように被害を具体的に示すことが重要だ。

脆弱性の技術名よりも「何が起きるか」「誰が影響を受けるか」を前面に出す。

### 対策指針

脆弱性ごとの対策とは別に、全体的な対策の方向性を示す。

**早急の対策**では、発見した脆弱性の大半がプログラムの実装上の不備に起因しており、該当箇所を適切に修正することで一般的なセキュリティ水準に到達できる旨を記載する。

**恒久的な対策**では、なぜ脆弱性が混入したかの根本原因分析を促す。開発者のセキュリティ知識の不足・セキュアコーディング基準の未整備・開発後のテスト不足といった原因が多く、開発プロセス全体の継続的な改善を推奨する内容にする。

## 10-3 危険度の評価基準

各脆弱性に危険度を付ける。実務で使われる基準は以下の通りだ。

| 危険度 | 目安 |
|---|---|
| **Critical** | 攻撃手順が明確で、悪用されれば深刻な被害が即座に発生しうる |
| **High** | 悪用されると情報漏えいやサービス停止など大きな被害につながる |
| **Medium** | 単独では影響が限定的だが、他の脆弱性と組み合わさると実害に発展しうる |
| **Low** | 直接の被害は小さいが、攻撃の足掛かりや被害拡大につながる可能性がある |
| **Information** | 脆弱性ではなく、セキュリティ強化のための推奨事項 |

CriticalとHighは早急な対応が必要だ。MediumとLowは計画的に対処する。Informationは必須ではないが対応することでより安全になる改善点だ。

## 10-4 各脆弱性の書き方（詳細セクション）

各脆弱性の詳細セクションは、おおむね以下の流れで書く。

- 危険度と攻撃の難しさ（容易・中・困難など）
- 何の問題か・悪用されるとどうなるか
- 実際に検証した手順（HTTPリクエストとレスポンスの抜粋）
- 推奨する対策
- 該当するURL・パラメータの一覧

### 説明の書き方

説明は「何の脆弱性か」と「その影響」をセットで書く。

**良い例：**「SQLインジェクションの脆弱性を確認しました。入力値がSQL文に直接組み込まれているため、悪用されるとデータベース内の情報が外部に流出する可能性があります。早急な対応を推奨します。」

**避けるべき例：**「SQLインジェクションがあります。」（影響が不明）

### 検証例の書き方

実際に操作した手順を再現できるように書く。HTTPリクエストとレスポンスを抜粋で記載する。

```
検証例：ログイン画面
username パラメータに ' OR 1=1-- を入力して送信する

リクエスト（抜粋）：
POST /api/login HTTP/1.1
Host: example.com
{"username": "' OR 1=1--", "password": "test"}

レスポンス：
HTTP/1.1 200 OK
{"status": "success", "user": "admin"}

→ ログインに成功したことが確認できる
```

スクリーンショットも必ず添付する。テキストだけでは再現の根拠が弱くなる。

## 10-5 エビデンス（証跡）の取り方

報告書に貼り付けるエビデンスは、以下の3点を必ず揃える。

1. **正常時のリクエスト・レスポンス**（比較のベースライン）
2. **検査文字を入力した後のリクエスト・レスポンス**
3. **画面のスクリーンショット**（脆弱性が確認できる状態）

スクリーンショットを撮るときは第2章で説明した診断専用プロファイルを使い、個人情報が映り込まないようにする。

---

## 10-6 報告書を書く際の注意点

**技術用語の説明を省かない**
クライアントが技術者とは限らない。「XSS」「CSRF」などは初出時に日本語の正式名称も併記する。

**「推測」と「確認」を区別する**
実際に再現できた脆弱性と、構造上存在すると推測される問題は明確に書き分ける。
- 確認できた場合：「〜であることを確認しました」
- 推測の場合：「〜と推測されます」

**該当箇所を漏らさない**
同じ脆弱性が複数箇所にある場合、すべてのURL・パラメータを列挙する。一部だけ修正されて残りが見落とされるのを防ぐためだ。

---

## 10-7 再診断報告書の書き方

再診断の結果は、初回報告書の指摘一覧に対してステータスを追記する形で記載する。

| ステータス | 意味 |
|---|---|
| **修正済み** | 再診断で脆弱性が再現しなくなったことを確認した |
| **未修正** | 対応されていないか、修正が不十分で引き続き再現する |
| **対応見送り** | クライアントがリスクを把握した上で今回は対応しないと判断した |

再診断時も「修正済み」の根拠となるHTTPリクエスト・レスポンスのエビデンスを添付する。「修正したつもりだったが別のパラメータで再現できた」というケースがあるため、単に「動作確認OK」だけでは不十分だ。

## 10-8 報告書作成の実務的なコツ

**テンプレートを使い回す**
各脆弱性の説明文・対策文は案件をまたいでほぼ同じ内容になる。一度書いた文章をテンプレート化しておくと、次の案件から大幅に時間を短縮できる。実務でも会社単位でテンプレートを管理しているケースがほとんどだ。

**チェックリストと紐付ける**
診断中にチェックリストで記録した結果をそのまま報告書に転記できるよう、チェックリストの項目と報告書の指摘番号を対応させておくと作業が効率的になる。

**最後に読み直す**
提出前に技術者でない視点で一度読み直す。「これを読んだクライアントが何をすべきかわかるか」を確認することが品質の最終チェックになる。

## 10-9 会社によって異なる報告書の構成

第3章のヒアリングシートと同様に、報告書のテンプレートも会社によって構成が異なる。実際に使用したテンプレートを比較すると、次のような違いがあった。

### 目次の順序

報告書の目次構成は会社によって大きく3パターンに分かれる。

- **サマリー先頭型**：経営層が最初に読む想定で、総評・リスクの概要を冒頭に置く
- **診断結果先頭型**：指摘一覧をまず示す実務優先の構成
- **診断概要先頭型**：診断の前提・期間・対象を最初に説明してから結果に進む

どのパターンが正解というわけではなく、クライアントへの伝わり方の方針が反映されている。

### 総合評価の表現方法

総合評価の表し方も会社によって異なる。

**危険度レベル型**
検出された脆弱性の中で最も高い危険度（Critical/High/Medium 等）を総合評価として使う。直感的にわかりやすい。

**件数一覧型**
High/Medium/Low/Informationの件数を表で示し、総合的な傾向を読み取れる形にする。複数の観点を並列で見せたい場合に向いている。

### 会社によって独自にあるセクション

担当した案件を通じて、一部の会社にしかないセクションをいくつか見かけた。

**脆弱性を被害の種類で整理するセクション**
指摘した脆弱性を技術的な分類ではなく「どんな被害につながるか」という観点で整理し直すセクションを持つ会社がある。技術的な知識がないクライアント担当者でも自社へのリスクを理解しやすくなるという利点がある。

**診断後の対応を案内するセクション**
診断が終わった後にクライアント側でやるべきことを報告書に明示する会社もある。テストで使ったアカウントやデータの後処理など、見落としやすい点を案内する目的だ。

**セキュリティ製品との対応を示す付録**
指摘した脆弱性を既存のセキュリティ製品で防御できるかどうかを示す付録を添付する会社もある。すでにセキュリティ製品を導入しているクライアントへの補足情報として機能する。
