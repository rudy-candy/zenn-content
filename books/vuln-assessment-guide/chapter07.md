## 7-1 この章で扱う脆弱性

認証・セッション関連の脆弱性は、実務の診断で最も頻繁に検出されるカテゴリのひとつだ。単体では危険度が低くても、他の脆弱性と組み合わさると深刻な被害につながる。

この章では以下の4つを扱う。

| 脆弱性 | 危険度 |
|---|---|
| ログイン試行回数の制限なし | Low |
| ログアウト後もセッションが有効な状態 | Low |
| セッションフィクセーション | Medium |
| 弱いパスワードが設定できてしまう | Low（推奨事項） |

---

## 7-2 ログイン試行回数の制限なし

ログイン画面でパスワードを何度間違えてもアカウントがロックされない状態だ。

攻撃者はこれを利用して、パスワードの候補リストを使った辞書攻撃や、すべての組み合わせを試すブルートフォース攻撃を自動で仕掛けられる。ログイン画面がある診断対象では必ず確認する項目のひとつだ。

### どう確認するか

同一のIDに対してパスワードをわざと複数回連続で間違え、その後に正しいパスワードでログインできるかどうかを確認する。ログインできれば対策がない。

実務では10回程度試して判定することが多い。試行回数はシステムによって異なるため、あまりに多く試すと実際のアカウントに影響が出る可能性もある。本番環境では特にテスト用アカウントで確認するのが原則だ。

### 対策

ログイン失敗が一定回数を超えた場合にアカウントを一時ロックする。ロック後は本人確認のためメール通知を送ること、管理者側でもロック状態を把握できることが望ましい。

---

## 7-3 ログアウト後もセッションが有効な状態

ログアウトボタンを押した後も、サーバー側でセッションが生きたままになっている状態だ。

一見すると「ログアウトできた」ように見えるが、ログアウト前に使っていたセッションIDをBurp Suiteで控えておき、ログアウト後にそのIDを使って直接画面にアクセスすると、ログイン済みの状態に戻れてしまう。共用PCや盗み見られた通信からの不正アクセスに悪用されるリスクがある。

### どう確認するか

1. ログイン後、Burp SuiteのHTTP historyでCookieのセッションIDを確認して控える
2. ログアウトボタンを押す
3. Burp SuiteのRepeaterで以下のヘッダを追加し、ログイン後の画面URLにリクエストを送る

```
Pragma: no-cache
Cache-Control: no-cache
```

このヘッダを追加する理由は、ブラウザのキャッシュを使わずにサーバーから直接レスポンスを取得するためだ。これを省くとブラウザのキャッシュが返ってきてしまい、正確な結果が得られない。

4. ログイン後の画面が表示されれば、セッションがサーバー側でまだ有効な状態だ。

### 対策

サーバー側でセッションを完全に破棄する処理をログアウト時に実装する。ブラウザ上のCookieを削除するだけでは不十分で、サーバー側に保存されているセッション情報自体を無効化しなければならない。

## 7-4 セッションフィクセーション

ログインの前後でセッションIDが変わらない状態だ。セッションフィクセーションとも呼ばれる。

攻撃者がこれを悪用するシナリオはこうだ。まず攻撃者が対象サイトにアクセスし、ログイン前のセッションIDを入手する。次にそのIDを被害者のブラウザにセットした状態で被害者にログインさせる。ログイン前後でセッションIDが変わらないため、攻撃者は自分が知っているIDを使ってそのままログイン済みの状態でアクセスできてしまう。

### どう確認するか

2つのブラウザを並べて検証する。

1. ChromeでサイトにアクセスしてCookieのセッションIDを取得する（まだログインしない）
2. そのセッションIDをFirefoxのCookieに手動でセットする
3. Firefoxでログインする
4. Chromeで同じセッションIDのまま、ログイン後の画面にアクセスできるかを確認する

アクセスできればログイン前のセッションIDがログイン後もそのまま使われている、つまりセッションが固定されている状態だ。

### 対策

ログインが成功した時点でセッションIDを新しい値に切り替える。ログイン前と後でIDが変わることを確認するのが最も確実な対策だ。

---

## 7-5 弱いパスワードが設定できてしまう

強度の低いパスワードを設定できてしまう状態だ。単体では危険度が低くても、7-2で説明したログイン試行回数の制限がない状態と組み合わさると、ブルートフォース攻撃が現実的な脅威になる。

### どう確認するか

パスワード設定・変更画面で、極端に弱いパスワードが登録できるかどうかを試す。

- 数字だけ（例：`1111`）
- 1文字（例：`a`）
- ログインIDと同じ値
- 同じ文字の連続（例：`aaaaaaa`）

実際の診断でも、1文字や数字のみのパスワードが普通に設定できるシステムに遭遇することがあった。開発段階でテスト用に簡単なパスワードを使えるようにしたまま、本番にそのまま出てしまっているケースが多い印象だ。

### 対策

最低限の強度を要求する設定を実装する。業界での一般的な目安は以下の通りだ。

| 項目 | 推奨値 |
|---|---|
| 最低文字数 | 8文字以上 |
| 使用可能文字種 | 英大文字・英小文字・数字・記号 |
| 組み合わせ強制 | 3種類以上を必須 |
| 同一文字の繰り返し | 不可 |
| ログインIDと同一 | 不可 |

## 7-6 その他の認証関連の確認事項

実務では上記4つに加えて、以下の項目も確認する。診断案件で繰り返し出てきた項目をまとめる。

### セッションIDがURLに含まれている

セッションIDがCookieではなくURLパラメータとして送信されているケースがある。

```
https://example.com/mypage?session_id=abc123
```

URLはブラウザの履歴・サーバーのアクセスログ・Refererヘッダに残るため、第三者にセッションIDが漏えいするリスクがある。セッションIDはCookieで管理するのが原則だ。

### 有効期限の長いセッション

セッションIDの有効期限が極端に長い（数日〜数ヶ月）場合、放置したブラウザや盗まれたCookieを使った不正アクセスのリスクが高まる。一定時間操作がない場合は自動でセッションを切る「タイムアウト」処理を実装するのが望ましい。報告書では危険度Lowで指摘されることが多い。

### パスワードリセット用トークンが推測できる

パスワードリセット用のトークンが推測可能な値（連番・短すぎる文字列など）である場合、第三者が他人のアカウントのパスワードをリセットできてしまう。リセットトークンは十分なランダム性を持つ値を使い、有効期限を短く設定することが対策の基本だ。

### 重要処理後のメール通知なし

パスワード変更・メールアドレス変更などの重要処理後に、登録済みメールアドレスへ通知が送られない場合も指摘対象となる。なりすましにより重要処理が実行されても本来のユーザーが気づく機会がなくなるためだ。危険度はInformationだが、実装コストが低い対策なので対応を推奨する。
