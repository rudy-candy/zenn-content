## 5-1 SQLインジェクションとは

SQLインジェクションとは、Webアプリがデータベースに問い合わせる際に使うSQL文に、悪意のある入力を「注入（inject）」することで、本来意図しない操作を引き起こす攻撃だ。

たとえばログイン画面でユーザー名に以下を入力するとどうなるか。

```
' OR 1=1 --
```

内部のSQL文が次のように変化する。

```sql
-- 本来のSQL
SELECT * FROM users WHERE username = '入力値' AND password = '入力値'

-- 注入後のSQL
SELECT * FROM users WHERE username = '' OR 1=1 --' AND password = '入力値'
```

`OR 1=1` は常に真であるため、パスワードなしで全ユーザーのデータが返ってくる。`--` 以降はSQLのコメントとして無視される。

これがSQLインジェクションの基本的な仕組みだ。実際の攻撃では、データの盗取・改ざん・削除、さらにはサーバーへのOSコマンド実行まで発展する可能性がある。

## 5-2 診断での確認手順

実務では以下の手順でSQLインジェクションを確認する。

### ステップ1：入力箇所の特定

クローリングで記録したリクエストの中から、パラメータに値を送信している箇所を探す。検索フォーム・ログイン画面・URLのクエリパラメータ（`?id=1` など）が主な対象だ。

### ステップ2：検査文字の入力

対象パラメータに以下の文字を入力し、レスポンスの変化を観察する。

| 検査文字 | 目的 |
|---|---|
| `'`（シングルクォート） | SQL文の構文を崩してエラーを引き起こす |
| `"`（ダブルクォート） | ダブルクォートで囲まれた値への対策漏れを確認 |
| `'--` | コメントアウトによる後続条件の無効化 |
| `' OR 1=1--` | 常に真となる条件を注入 |

### ステップ3：レスポンスの確認

検査文字を入力した後、以下の3パターンに分類して判定する。

**エラーが発生した場合**
「MySQLエラー」「SQL構文エラー」などのメッセージが表示されれば、SQL文が正常にエスケープされていない証拠だ。DBMSの種類（MySQL・SQL Server・Oracle・PostgreSQLなど）がエラーメッセージに含まれることもある。

**レスポンスが変化した場合（エラーなし）**
エラーは出ないが、表示される件数や内容が変わる場合はブラインドSQLインジェクションの可能性がある。

**変化がない場合**
適切にエスケープ・バリデーションが実装されている可能性が高い。ただしWAFによってブロックされている場合もあるため、複数の検査文字で試すことが重要だ。

### ステップ4：時間遅延による確認

エラーも変化も見えないケースで使うのが「時間遅延」の手法だ。

```
;/bin/sleep 20
```

このコマンドがDBMSに渡されてサーバーが20秒応答を遅らせた場合、SQLが実行されたことを意味する。エラーが出なくても脆弱性が存在するケースで有効だ。

## 5-3 Burp Suiteでの操作

Burp Suiteを使うと、検査文字の入力と確認が効率的に行える。

1. Proxy → HTTP historyで対象リクエストを選択
2. 右クリック → 「Send to Repeater」を選択
3. RepeaterでパラメータのValueを検査文字に書き換えて送信
4. Responseタブでエラーメッセージや挙動の変化を確認

Repeaterは同じリクエストを何度でも書き換えて送れるため、複数の検査文字を素早く試せる。

## 5-4 実務での注意点

**対象DBMSによって挙動が変わる**
MySQL・SQL Server・Oracle・PostgreSQLはそれぞれSQL構文やエラーメッセージが異なる。ヒアリングシートで確認したDBMSの種類に合わせて検査文字を使い分けると効率が上がる。

**WAFに検知されることがある**
シングルクォートやUNION句などはWAFの検知パターンに含まれることが多い。検査中にアクセスがブロックされた場合は、クライアントにWAFのホワイトリスト登録を依頼する。

**本番環境では慎重に**
時間遅延系の検査はサーバーに一定の負荷をかける。本番環境では実施可否をクライアントと事前に確認しておくことが重要だ（第3章3-1参照）。

## 5-5 実際の診断で見つかった代表的なパターン

複数の案件を通じて、SQLインジェクションが検出されるパターンはいくつかに収束する。報告書に実際に記載された検証手法をもとに整理する。

### パターン①：真偽条件の比較（最も多い）

パラメータに `AND 1=1`（常に真）と `AND 1=2`（常に偽）を付加してレスポンスを比較する手法だ。

```
パラメータの正常値：18
変更後①：18 AND 1=1   → レスポンスA（正常に処理される）
変更後②：18 AND 1=2   → レスポンスB（処理が変化する）
```

AとBのレスポンスが異なった場合、SQL文に条件式が追加できたことを意味する。エラーメッセージが表示されなくても検出できるため、エラーが隠蔽されているシステムでも有効だ。

報告書では、`AND 1=1` と `AND 1=2` でレスポンスが変化した事実と、それがSQL文に外部から条件式を追加できたことを意味する旨を記載し、SQLインジェクション脆弱性が存在すると推測される根拠として示す。

### パターン②：コメントアウト

`--`（SQLのコメント記号）を使ってSQL文の後続部分を無効化する手法だ。

```
パラメータの正常値：100
変更後①：100-    → 「-」が不正な構文としてエラーになる
変更後②：100--   → 「--」がコメントアウトとして解釈され正常に処理される
```

`-` では構文エラーになるが `--` では正常処理されるという挙動の差がSQLインジェクションの証拠となる。

### パターン③：時間遅延

エラーも挙動の変化も見えない場合に使う手法だ。OSコマンド `sleep` をSQL文に注入し、サーバーの応答時間が意図した秒数だけ遅延するかを確認する。

```
検査文字列：; /bin/sleep 20
```

正常時は即座に応答するが、SQLが実行されると20秒後に応答が返ってくる。応答時間の変化が確認できれば脆弱性が存在する。

## 5-6 実際の報告書から見るエラーの種類

実務の報告書では、SQLインジェクションの検出結果は危険度によって記述が変わる。

### 危険度「High」の場合（深刻）

パラメータを操作することで実際にデータベースの内容を取得・操作できた場合は最高レベルの危険度となる。報告書の説明欄には、脆弱性の存在・悪用された場合の被害範囲（データベース内の全情報漏えいの可能性）・早急な修正の必要性をセットで記載する。

検証例には実際のHTTPリクエストと、パラメータを改ざんした際のレスポンスが記載される。

### 危険度「Information」の場合（足掛かり）

実害は出ていないが、エラーレスポンスにSQL構文が含まれているケースがある。

```
HTTP/2 400 Bad Request
Content-Type: application/json; charset=utf-8
...
{"error": "SQL syntax error near 'id' at line 1"}
```

このような場合、攻撃者にDBMSの種類や内部構造を推測させる情報を与えることになる。実害がないため危険度は低いが、報告書にはエラーレスポンスにSQL構文が含まれている事実と、それが攻撃の足掛かりになりうる旨を記載する。

## 5-7 対策

SQLインジェクションの根本対策は**プリペアドステートメント（バインド機構）の使用**だ。

通常のSQL文ではパラメータを文字列として直接組み込むため、特殊文字が混入するとSQL構文が変化してしまう。プリペアドステートメントを使うと、パラメータと命令が分離されるため、どんな文字列を入力されても命令部分が変化しない。

```sql
-- 危険な実装（文字列結合）
"SELECT * FROM users WHERE id = " + user_input

-- 安全な実装（プリペアドステートメント）
"SELECT * FROM users WHERE id = ?" → バインド変数にuser_inputを渡す
```

加えて**入力値のバリデーション**も有効だ。数値のみを受け付けるパラメータに文字列を渡せないよう制限するだけで、多くの攻撃を防げる。
