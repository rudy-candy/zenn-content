CyLab Security Academy（旧picoCTF）の DISKO 2 を解きました。前作の DISKO 1 で覚えた手をそのまま使ったら、フラグ候補が125個出てきました。

```bash
$ strings disko-2.dd | grep -o "picoCTF{[^}]*}" | sort -u | wc -l
125
```

DISKO 1 は `strings` を1回かけるだけで終わる問題でした（[そのときの記事](https://zenn.dev/rudy_candy/articles/disko-1-picoctf-writeup)）。「ディスクイメージはまず `strings`」は、そこで覚えた順番です。DISKO 2 は、その順番を覚えた人をちょうど狙ってきます。

## 125個は全部同じ顔をしていた

```
picoCTF{4_P4Rt_1t_i5_033c9baa}
picoCTF{4_P4Rt_1t_i5_039aca3b}
picoCTF{4_P4Rt_1t_i5_03a3a9bc}
...
```

違うのは末尾の8文字だけです。前半の `4_P4Rt_1t_i5` は「a part it is」。パーティションの話をしているのは分かりましたが、125個を見た瞬間は、どれが本物かを見分ける材料が手元に何もありませんでした。

## 答えは問題文に書いてあった

問題文はこうです。

> The right one is Linux! One wrong step and its all gone!

最初に読んだとき、私はこの一文をほとんど読み流していました。ディスクの中にはLinuxとFAT32の2つのパーティションがあって、正解はLinuxの方にある。そう書いてあったわけです。

あとでおとりの置き場所を数えてみると、こうなっていました。

| 場所 | 個数 |
|---|---|
| パーティション表の外（未割当の領域） | 75 |
| FAT32 | 50 |
| Linux | **1** |

`strings` は、ファイルシステムもパーティションも気にせず、ディスク全体から文字列を拾います。DISKO 1 ではその性質に助けられました。DISKO 2 では、同じ性質のせいでおとりを全部拾うことになります。

## 気づいたこと：候補が複数出たら「どこから出たか」で選ぶ

`strings` を最初に打つ順番は、今も間違っていないと思っています。足りなかったのは、結果が複数出たときの次の一手でした。

1. `strings` で全体を見る
2. 候補が複数出たら、パーティション表を見る
3. 条件に合うパーティションだけを切り出して、もう一度 `strings`

私の本業は脆弱性診断です。そこでも「この文字列は本当にサーバーの処理結果なのか、それともキャッシュやエラーページから来たものなのか」を確かめないと、誤検知を報告書に書くことになります。CTFでも結局そこを確かめる羽目になったので、ちょっと笑いました。

## もう1つ：今のフラグは picoCTF{ ではなく academy{

この記事を書くために、CyLab から配布ファイルを落とし直して解き直しました。ところが、同じ手順でフラグが1つも出ません。当時のファイルとハッシュも違ったので、てっきりフラグが消されたのだと思い込みました。

一番簡単な問題を落とし直して、やっと分かりました。今のフラグは `academy{...}` で始まります。改名に合わせて形式が変わっていて、`picoCTF{` で `grep` していたから0件だっただけでした。当時のフラグは今は通りません。

昔のwriteupを見ながら解く人は、検索語を `academy{` に変えてください。

## 詳しい手順

パーティション表の読み方、`dd` の `skip` と `count` の決め方、おとり125個の位置を数えたコマンド、今のフラグ形式で解き直した結果まで、手順を全部書いた記事はnoteに置いています。
