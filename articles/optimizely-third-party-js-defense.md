2026年11月16日、ABテストの基盤として広く使われている Optimizely が侵害され、その配信コードを読み込んでいた多数のサイトに、悪性の JavaScript が一時的に配られました。Zoom・GitLab・CNN・BBC・Salesforce といった名前が並び、調査した研究者の集計では178組織・188ファイルに影響が及んだとされています。

私は Web アプリの脆弱性診断をしていて、自分で CDN を攻撃することはありません。ただ、この手の「自分のサイトは直していないのに、読み込んでいる外部スクリプト経由でマルウェアが配られる」事案は、診断でも設計レビューでも必ず話題になるところです。この記事では、今回の件を一次情報で確認したうえで、サイトを持っている側が「自分の読み込んでいる外部スクリプトをどう確認し、どう守るか」を、実務の視点で整理します。攻撃のやり方そのものは扱いません。

Web のセキュリティ設定を診断の観点からまとめた本も公開しています。外部スクリプトやヘッダの確認もこの中で扱っています。

## 何が起きたのか（事実の確認）

報じられている事実を、ベンダー発表と研究者の調査から拾うと、次のようになります。

- 攻撃者は Optimizely の Experimentation アカウントの登録フローにあった弱点を突き、一部の顧客プロジェクトに悪性の JavaScript を注入した（Optimizely 発表）
- 汚染されたファイルは、正規の配信ホストである `cdn.optimizely.com` からそのまま配られた。つまり通信は HTTPS で、証明書も正規のものだった
- 注入コードは外部から追加のスクリプトを読み込み、決済カード情報の窃取や暗号資産ウォレットアドレスの書き換えなどを行う作りだったと報告されている
- Optimizely は同日中に弱点の遮断・修正の展開・注入コードの除去・配信のブロックを実施し、研究者の監視でも同日中にはほぼすべてのファイルがクリーンに戻ったとされている
- 本稿の時点で、この件に対する CVE 番号は確認できていない

## なぜ HTTPS でも防げなかったのか

この件でいちばん大事なのは、**正規のホストから、正規の証明書で、汚染されたファイルが配られた**という点です。

HTTPS は「通信の途中で誰かに書き換えられていないこと」を保証します。しかし今回書き換えられたのは通信経路ではなく、配信元のファイルそのものです。ブラウザから見れば、いつもの `cdn.optimizely.com` に、いつもの証明書で、正しくつながっている。鍵マークは何も異常を示しません。

私が診断の報告書で「外部スクリプトの読み込みはリスクになり得ます」と書くとき、根っこにあるのはこの構造です。自分のサーバーをどれだけ固めても、`<script src="他社のドメイン">` を1行書いた瞬間、そのドメインの中身を信頼し続けることになる。相手が侵害されれば、こちらのページ上で任意の JavaScript が動きます。読み込んでいるのが解析タグでも、ABテストでも、チャットウィジェットでも同じです。

## 守る側がまず確認すること

攻撃する側の話ではなく、**自分のサイトで何を確認できるか**を順に挙げます。どれも許可された自分の資産に対して実施する前提です。

### 1. 何を読み込んでいるかを棚卸しする

最初の一歩は、自分のページが外部からどんなスクリプトを読み込んでいるかを把握することです。ブラウザの開発者ツールのネットワークタブを開き、ドメインでフィルタすれば、自ドメイン以外から来ている `.js` が並びます。ここに、担当者も忘れていた古いタグが残っていることは珍しくありません。

診断でも、まずこの一覧を作るところから始めます。「このスクリプトは誰が、いつ、何のために入れたのか」を言える状態になっていないと、その1本が侵害されたときに気づけません。

### 2. CSP でスクリプトの出どころを絞る

Content Security Policy（CSP）は、「このページで実行してよいスクリプトの出どころ」をブラウザに宣言する仕組みです。`script-src` に許可したホスト以外からのスクリプトは、ブラウザがブロックします。

今回の件で示唆的だったのは、研究者が調べた影響サイトのうち、多くが CSP を設定していないか、設定していても許可範囲が広すぎてスクリプトが実行されてしまった、という指摘です。CSP は「入れれば安心」ではなく、`script-src` をどこまで絞れているかで効き目が変わります。`*` や広いワイルドカードを許可していると、宣言しているだけで実際には止まりません。

ここで注意したいのが、今回のように**許可したホスト自体（`cdn.optimizely.com`）が汚染される**ケースです。CSP で許可している以上、そのホストからのスクリプトは通ります。つまり CSP は「知らないホストからの読み込み」は止められても、「許可済みホストの中身の変化」までは止められません。だからこそ、許可するホストを必要最小限に保つこと、そして次の監視が効いてきます。

### 3. CSP のレポート機能で異常に気づく

CSP には、ポリシー違反が起きたときにその情報を指定した先へ送る `report-to`（旧 `report-uri`）という仕組みがあります。これを有効にしておくと、「許可していないスクリプトが読み込まれようとした」「許可していない接続先へ通信しようとした」といった出来事が記録されます。

今回の汚染コードは外部の見慣れないドメインへ通信しようとしていました。もし `connect-src` を絞ってレポートを受けていれば、「このページから知らないドメインへ通信が飛ぼうとしている」という違反として現れた可能性があります。守りを1枚増やすだけでなく、「何かおかしい」に早く気づくための計測として、このレポート機能は実務でも勧めています。

### 4. SRI が効く場所と効かない場所を見分ける

Subresource Integrity（SRI）は、読み込む外部ファイルのハッシュを `integrity` 属性に書いておき、中身が1バイトでも変わったらブラウザが実行を拒否する仕組みです。CDN から配る固定のライブラリ（バージョン固定の js など）には、とても有効です。

一方で、今回の Optimizely のように**中身が動的に変わる前提のタグ**には、SRI は素直には使えません。ハッシュを固定できないからです。ここを混同して「SRI を入れておけば外部スクリプトは安全」と考えると、効かない場所に対策した気になってしまいます。固定配信のファイルには SRI、動的なタグには CSP と出どころの最小化・監視、という使い分けが現実的です。

## 診断の仕事とのつながり

私が Web 診断でサードパーティスクリプトの話をするとき、伝えたいのは「外部スクリプトを使うな」ではありません。解析もABテストも、ビジネスには必要です。伝えたいのは、**それが1本増えるごとに信頼する相手が1社増える**という事実を、設計の段階で意識してほしいということです。

今回の件は、復旧がとても速かった事案でもあります。ベンダーが同日中に遮断・修正まで動いたのは評価できる対応でした。ただ、利用する側にできることは残ります。読み込むものを棚卸しし、CSP で出どころを絞り、レポートで異変に気づけるようにしておく。この3つは、次に別のどこかが侵害されたときにも、そのまま効きます。

## まとめ

- HTTPS や証明書は「通信の途中の改ざん」を防ぐが、「配信元のファイルそのものの汚染」は防げない
- 外部スクリプトを読み込むことは、その配信元を信頼し続けること。まず何を読み込んでいるかを棚卸しする
- CSP は `script-src` を最小限に絞ってこそ効く。レポート機能で異変に気づけるようにしておく
- SRI は固定配信のファイルには有効、動的に変わるタグには使いにくい。場所で使い分ける
